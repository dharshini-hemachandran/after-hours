Campus Connect

Skill Passport: matching students to opportunities by what they can show, not how they format a résumé.

Open the live project ↗Source on GitHub ↗
The problemi

A résumé lists claims. It rarely shows ability.

A résumé tells an organiser little about what a student can actually do, and good candidates are easy to miss when discovery depends on how a document happens to be worded.

Product conceptii

A passport, not a document

Each student builds a skill passport: skills, projects and achievements with evidence attached. Organisers search opportunities and candidates through the passport rather than a bare PDF.

StudentsBuild a passport, analyse a résumé, find matching opportunities and attempt timed skill-specific challenges.
OrganisersPublish opportunities, find matching candidates and review challenge submissions.

Decisions that shaped the product

Honest verification. A challenge result reads “automated check only” until a human reviewer has scored the rubric. Student control. Students choose who can open the full passport: private, applicants only, or any organiser account. Every view is logged. Consent. Résumé text is stored only after the student chooses to add it.

Matchingiii

How matching works

The current method is classical information retrieval: TF-IDF vectors compared with cosine similarity. It is not a trained neural network and not a supervised predictive model.

1Clean the text of a résumé or profile
2Extract skills from it
3Weight each term: term frequency × inverse document frequency
4Compare with each opportunity by cosine similarity
5Rank the best matches

Try the method

This runs the same arithmetic in your browser against five illustrative opportunities. They are examples for the demonstration, not real listings.

    What TF-IDF cannot doIt matches shared terms. It does not understand meaning beyond the words used, which is why the product pairs it with evidence and challenges.
    Systemsiv

    Architecture

    Front endStatic site on GitHub Pages
    APIFastAPI service on Render
    DatabasePostgreSQL on Neon

    Features

    Résumé analysis accepts .txt, text-based .pdf and .docx files up to 10 MB. Skill challenges are short and timed; briefs are written by Claude when an API key is configured on the service, otherwise by built-in templates. Accounts use password hashing and bearer-token sessions.

    Current limitationsScanned PDFs need OCR, which is not yet supported. The starter keeps shared state in one database record, so it is meant for a single API instance.

    Future development

    Move to transactional per-entity tables before running several API instances, and add OCR for scanned résumés.
